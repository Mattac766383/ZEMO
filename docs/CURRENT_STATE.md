Residual in-crate helpers may exist for tests/platform code but are not the production desktop mutation path.
- Journal/executor coordination: durable intent and rollback metadata are committed before mutation; executor responses are recorded with request identity/state. Ambiguous executor outcomes force recovery without blind retry. Duplicate execution of the same approved request is rejected.
- Crash recovery and restart safety: interrupted forward/rollback sessions enter recovery, block new executions, and reconcile PREPARED / applied / restored / ambiguous states from journal plus live filesystem observation. Executor or coordinator restart does not auto-resume forward mutation. Forward resume remains **NOT IMPLEMENTED**.
- Rollback hardening: rollback revalidates live identity/hash and no-overwrite conditions; external modification, occupied original path, or nonempty created directories yield honest partial/blocked outcomes rather than overwrite.
- Journal corruption handling: authenticated journal/database diagnostics can lock Apply into a fail-closed recovery/diagnostics state (`journal_locked`) instead of silently mutating. Repair/purge automation is not implemented.

- Symlink/reparse hardening: preflight and worker-side validation reject symlink/reparse redirection, traversal, and unsafe destination occupancy; Windows adapters prefer non-reparse identity checks where available.
- Case-only rename: staging path exists and can be enabled by an explicit qualified policy flag; default production policy keeps case-only rename gated until genuine NTFS qualification.
- Cross-volume move: **NOT IMPLEMENTED**.

## Milestone 8 — Safety-gated filesystem application

- Status: **PARTIAL**, superseded for trust-boundary closure by Milestone 8.1. The original M8 application/recovery protocol remains the foundation and still passes against an isolated mutation sandbox. Production Apply remains disabled outside Windows; native Windows/NTFS execution has not yet been runtime-qualified.
- Authority boundary: React has no generic path-based move/delete API. Tauri exposes only execution IDs and proposal IDs through `prepare_execution`, consent challenge/finalize, start, pause/cancel, status/history, recovery, and rollback commands. Rust reloads the approved proposal and current revision from encrypted SQLite; frontend-supplied operation lists are never trusted.
- Approval and frozen intent: an `ApprovedExecutionPlan` binds execution/plan/proposal/revision/source-scan IDs, the exact proposal-operation IDs, operation count, consent state, and a BLAKE3 digest of canonical plan material. Proposal status/revision is checked at preparation, attestation, and start. Preparation never mutates files; final consent is plan-bound and Rust-attested (see Milestone 8.1). Batches of 1,000+ require the exact `ORGANIZE` phrase.
- Preflight and drift: every eligible operation revalidates relative path, explicit root, regular-file/non-link state, stable native identity, single-link state, volume, size, modified time, and streaming BLAKE3 content digest immediately before scheduling and again immediately before mutation. Missing/changed sources, stale/review-only operations, occupied/unsafe destinations, unqualified case-only renames, duplicate case-insensitive targets, and blocked dependencies fail closed. Independent safe operations may remain confirmable; unsafe operations remain visible as blocked/stale.
- Planning: plans are frozen before confirmation and ordered deterministically. Required directories are shallow-to-deep; destination/source dependencies are topologically ordered. Cycles/swaps use UUIDv7 names below `.supremacy-staging/<execution-id>`, with every staging step included in the plan, journal, recovery, and reverse rollback order.
- Supported mutation: approved directory creation plus same-volume move, rename, and move+rename. Destination overwrite, delete, trash, duplicate cleanup, arbitrary copy, shell execution, privilege elevation, and automatic/background organization do not exist. On Windows production, mutations are performed by the authenticated isolated executor rather than in-process Tauri mutation.
- Cross-volume and case policy: cross-volume move is **NOT IMPLEMENTED** and leaves the source untouched. Case-only rename remains production-gated until native NTFS behavior is qualified. Production execution additionally requires a local fixed NTFS root; removable/non-local volumes fail closed.
- Path/self protection: the centralized policy combines an explicit canonical root with Windows-safe virtual-path validation, traversal/absolute/UNC/device-name/length checks, case-insensitive collision keys, symlink/reparse ancestor rejection, protected system roots, application data/database/journal/executable exclusions, and application-controlled staging names.
- Journal and durability: migrations `0008_safety_gated_filesystem_application.sql`, `0011_execution_consent_attestation.sql`, `0014_execution_safety_policy_v2.sql`, and `0015_cross_process_recovery_hardening.sql` cover execution sessions, consent attestation, policy/request identity, and cross-process recovery metadata. SQLite uses SQLCipher, WAL, `synchronous=FULL`, and transactional event/count updates. Durable intent and rollback metadata are committed before every native mutation.
- Journal security properties: SQLite stores a canonical BLAKE3-linked event chain and chain head. A separate append-only journal is XChaCha20-Poly1305 encrypted/authenticated with a key derived from the OS-protected database key, hash-chain checked, flushed, and `sync_all`ed. Startup validates and reconciles both stores; authenticated corruption can lock Apply into diagnostics rather than silent continue.
- Postconditions and batch control: an OS success is insufficient; destination identity/content and source absence are verified before `APPLIED`. Critical or dependency failures stop scheduling. Pause/cancel requests are observed only between recoverable operation units; an in-flight unit is never interrupted halfway by the scheduler.
- Recovery: startup converts interrupted forward/rollback sessions to recovery-required states, blocks every new execution globally, validates journals, and compares actual source/destination state. It distinguishes not-started, applied/restored, and ambiguous states. Ambiguity fails closed; no forward resume is offered.
- Rollback: only journaled applied/recovered operations are reversed, in reverse dependency order, after live identity/hash and no-overwrite checks. Directories are removed only when created by that execution and still empty. External modification, an occupied original path, or a nonempty directory yields honest `ROLLBACK_PARTIAL`; recent recovery/history records are not automatically purged.
- UX/history: the Organization Preview remains mandatory. The execution panel presents drift/block counts, plan-bound final confirmation, per-operation progress, safe pause/cancel, completion totals, activity history, rollback availability, Undo through the rollback engine, and a dedicated fail-closed recovery card.
- Privacy/security: execution is entirely local and adds no network client, analytics, telemetry, shell command, generic filesystem command, or privilege escalation. File paths, proposal state, execution errors, and journal records remain local. The earlier medium trust-boundary gaps (renderer-forgeable final consent and in-process production mutation) are closed by Milestone 8.1 on the Windows Apply path; residual limits are listed under Milestone 8.1.
- Validation: original M8 sandbox mutation/crash/recovery, operation/path/journal, persistence, and UI coverage remain; current focused counts are tracked under Milestone 8.1.
- M8 limitations carried forward: native Windows/NTFS behavior remains unvalidated; macOS production Apply is disabled; cross-volume move is unsupported; case-only rename is production-gated; real Windows locked-file/antivirus/disk-full behavior remain unfinished; the macOS sandbox 10k apply/verify/rollback qualification is recorded under Milestone 8.1; forward recovery resume is intentionally absent; aggressive retention/purge automation is not implemented.

## Milestone 5 — Local semantic understanding

- Status: **PASS** on the macOS development environment. Native Windows runtime validation remains pending.
- Architecture: semantic analysis consumes canonical Milestone 3 extraction records and never re-reads or mutates source files. `ScannerApplicationService` runs a bounded queue (two workers by default), supports cooperative cancellation and per-file text/time/output limits, and persists completed files incrementally.
- Provider strategy: `SemanticProvider` is a local-only, versioned abstraction. The production provider for this milestone is `DeterministicSemanticProvider` (regex, parsing, structural labels, and conservative heuristics). No LLM, model download, remote inference, cloud fallback, shell, or network capability is present.
- Result model: analyses, typed fields, per-file entities, candidates, conflicts, statuses (`PENDING` through `CANCELLED`), input quality, analyzer/provider/schema versions, and exact bounded confidence scores are represented explicitly. Confidence policy is centralized (`VERY_HIGH` >= 0.95, `HIGH` >= 0.85, `MEDIUM` >= 0.65); scores are ranking/quality signals, not calibrated probability guarantees.

- Structured fields: supplier/customer/issuer candidates, document/invoice/quote/reference identifiers, issue/due/expiration/signature dates, subtotal/tax/total/amount and currency, project/reference candidates, contract title, and parties are extracted only when evidence supports them.
- Normalization: supported French/English/ISO dates normalize to `YYYY-MM-DD`; ambiguous numeric dates remain ambiguous. Money uses signed integer minor units plus explicit currency, never floating-point storage or guessed currency. Identifiers retain original evidence and require credible labeled patterns.
- Explainability: every retained machine field/entity has bounded text/metadata evidence, offsets where available, extraction method, explanation, confidence, and analyzer version. Current upstream extraction is usually flattened text, so page/sheet provenance is preserved when supplied but is not reconstructed when absent.
- Quality and conflicts: missing/partial/OCR-degraded input lowers confidence and analysis status; empty input returns `UNKNOWN`. Evidence-backed competing values are retained and critical conflicts are routed to review rather than overwritten.
- Storage: migration `0005_local_semantic_understanding.sql` adds analysis batches, analyses, fields, entities, evidence, and separate user-correction tables plus document-type/context/status projections on local search records. M5 entity IDs remain scoped to a file analysis; M6 maps them into a separate cross-file identity layer without replacing them.
- Corrections and review: `USER_CONFIRMED` and `USER_CORRECTED` values are stored separately from machine values, remain authoritative after re-analysis, and can resolve relevant semantic review items. Review reasons are intentionally limited to ambiguity, conflicts, low-confidence type/context, and missing critical fields.
- UX: File Detail shows a concise Understanding summary, confidence language/percentages, fields, entities, competing candidates, expandable “Why?” evidence, and typed confirmation/correction controls. Batch understanding progress and cancellation are exposed through Tauri events.
